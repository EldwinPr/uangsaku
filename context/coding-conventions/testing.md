# Testing

What gets a test, at which layer, and the two requirements that need one specifically.

`general-rules.md`'s definition of done says verification must pass before an issue closes —
for a documentation issue that meant checking the artifact against its conventions; from
`FEAT01` onward it also means the test suite and the analyzer.

## The layers

| Layer | Tool | What it is for |
|---|---|---|
| **DAO / query** | `flutter_test` + `NativeDatabase.memory()` | The bulk of the value. Every derived figure in this app is a query, so this is where correctness lives. |
| **Notifier** | `flutter_test` + a `ProviderContainer` over an in-memory database | That a write produces the row it should. |
| **Widget** | `flutter_test` | That a screen renders what a provider gives it, and that its controls stay enabled. |
| **Migration** | generated by `drift_dev make-migrations` | That a schema change preserves data. Commit them; do not hand-write them. |

No integration-test tier for now. It is the slowest to write and maintain, and this app has
one user, one device and no network — the risk it would cover is small. Revisit if the app
ever grows a sync client.

## What is actually worth testing here

**Derived numbers, not plumbing.** NFR-2 says every figure has exactly one source and none are
stored, which means the entire correctness surface of this app is a set of SQL queries. Test
those hard:

- `UC-01`'s four figures with accounts in all three groups, including the case that motivated
  the requirement — a `RECEIVABLE` balance must **not** land in "spendable".
- `UC-12`'s budget consumption including the null-group **"Others"** bucket (FR-17), which is
  the case a naive `GROUP BY budget_group_id` silently drops.
- `UC-10`'s paid / remaining against a debt with repayments in both directions.
- **"Is this spending?"**: a transfer (FR-8) and a loan (FR-9) must not count as an expense.
  This is the single most valuable test in the project, because it is the requirement the
  owner stated most emphatically and the one a future query is most likely to get wrong.

**Empty and boundary states.** A month with no transactions, an account with no movements, a
budget with nothing spent against it. Each is a real screen on day one.

## Two requirements that need explicit tests

These are not ordinary correctness checks — they are project rules that will otherwise erode
quietly.

**NFR-4: no user action is refused.** The fit criterion is a count, and the count is zero.
Widget tests should assert that destructive and consequential controls are **enabled**:
deleting an account that has transactions, editing a budget period mid-month, changing the
currency after amounts exist. Each must proceed, warning at most. A disabled button is the
likeliest accidental violation in the whole app, because disabling one feels like good UI.

**FR-18: full CRUD, no entity is create-only.** For each entity, one test proving it can be
edited and deleted. Cheap, and it catches the case where an entity quietly ends up
create-only because no screen ever offered a delete.

## Conventions

- Test files sit beside the code under `test/`, mirroring `lib/src/`'s module folders, named
  `*_test.dart`.
- **A test names the requirement it defends** in its description:
  `test('FR-8: a transfer does not count as spending', ...)`. When a test fails two years from
  now, the question is always "was this rule real?" — the answer should be in the test name.
- Build the in-memory database fresh per test; do not share one across a file.
- No mocking of drift. An in-memory SQLite database is fast and real, and mocking the thing
  whose behaviour you are testing proves nothing.

## Running

```bash
flutter analyze          # must be clean; strict-casts etc. are in analysis_options.yaml
dart format --set-exit-if-changed .
flutter test
dart run build_runner build --delete-conflicting-outputs   # after schema or provider changes
```

All four before an issue closes. `flutter analyze` counts as verification in the
definition-of-done sense — a warning left in place is a decision to leave it, and should be
argued in the plan rather than ignored.

**These four now run in CI** (`.github/workflows/ci.yml`, added 2026-08-21), in that order but
with `build_runner` first — generated code has to exist before `analyze`, `format` and `test`
read it, and running it last only checks the previous commit's output. The Flutter job is
guarded on `pubspec.yaml` existing, so it passes trivially until `FEAT01` creates the project
rather than failing red for months. A second job runs `python audit.py`, which guards the
documentation the same way.

Running them locally before pushing is still the faster loop; CI is there because an
unattended implementation run has nothing else checking it.
